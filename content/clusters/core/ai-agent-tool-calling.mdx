# AI Agent Tool Calling

## Direct answer (AEO)

Tool calling is the primitive that turns a language model into an agent. The model emits a structured payload describing a tool invocation; the application executes the call; the result returns to the model. The model does not execute the call itself. The application is responsible for validating the call, dispatching it, validating the result, and returning it to the model.

## Key takeaways

- The model returns a **payload**; the application executes the **call**.
- Tool schemas are part of the contract; the model hallucinates less when the schema is precise.
- Every tool call needs **validation** (inbound and outbound) and **observability**.
- MCP standardises how tools are advertised and invoked. See [](/mcp) (when the MCP pillar ships).

## How tool calling works

```
[Model] → emits tool_call payload
[App]   → validates payload against tool schema
[App]   → executes call against external system
[App]   → validates result
[App]   → returns result to model
[Model] → reasons about result, decides next step
```

The key insight: the model never has network access. The application is the only thing that touches external systems.

## Tool schemas

Every tool the model can call has a schema:

- **Name** — what the model calls it.
- **Description** — what the model thinks it does.
- **Parameters** — the shape of the arguments the model must provide.
- **Return type** — what the application will return.

Schemas are part of the contract. The model hallucinates less when the schema is precise. The description is the model's only source of truth about the tool — write it for the model.

## Inbound validation

Before dispatching the tool call, validate the payload:

- Required arguments present.
- Argument types match the schema.
- Argument values are within allowed ranges.
- The user has permission to invoke this tool with these arguments.

Reject invalid calls. Do not dispatch them.

## Outbound validation

Before returning the result to the model, validate the result:

- Result shape matches the expected return type.
- Result is not an error or an ambiguous value.
- Result is safe to surface to the model (no prompt-injection content from untrusted sources).

Reject results that fail validation. Return an error to the model and let it reason about the failure.

## Engineering controls

| Control | Why |
|---------|-----|
| Schema validation (in + out) | Reduces hallucination and silent corruption |
| Per-tool permissioning | The agent can only call tools it has been granted |
| Argument scrubbing | Strip secrets, PII, and untrusted content from arguments |
| Result scrubbing | Strip prompt-injection content from results |
| Rate limiting | Prevent runaway tool calls |
| Logging | Every call, every result, every error, with correlation id |
| HITL | Human review before consequential calls |

## Failure modes

1. **Model hallucinates a tool name.** The application returns a "tool not found" error; the model retries with a corrected name.
2. **Model hallucinates arguments.** The application rejects the payload; the model retries with valid arguments.
3. **Tool returns garbage.** The application rejects the result; the model reasons about the failure and either retries or escalates.
4. **Tool call has side effects the model did not intend.** Engineering control: HITL for consequential tools; sandboxing for exploratory tools.

## MCP standardisation

The [Model Context Protocol specification, revision 2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18) standardises how tools are advertised (the `tools/list` method) and invoked (the `tools/call` method) so that a model and a tool server can communicate without bespoke integration code per pair. ## Frequently asked questions

### Does the model ever execute tool calls directly?

No. The model returns a payload; the application executes the call. The application is the only thing that touches external systems. This is the security boundary.

### How do I prevent a model from hallucinating tool names?

Use a tight tool schema and validate the tool name before dispatch. If the model hallucinates, the validation fails and the model retries with a corrected name (or escalates).

### What if a tool call has destructive side effects?

Put the tool behind a HITL checkpoint. See [](/human-in-the-loop-agents). For exploratory tasks, run the tool in a sandboxed environment.

### Can a model call multiple tools in one turn?

Yes. Modern tool-calling APIs support parallel tool calls in a single response. The application dispatches them in parallel and returns the results. This is faster but harder to debug — validate and log each call independently.

### Should I expose every API endpoint as a tool?

No. Expose only the endpoints the agent needs. Each tool is a permission grant. The narrower the tool surface, the smaller the blast radius if the model misuses a tool.

### How do I version tool schemas?

Version every tool schema. When the schema changes, the agent framework must be told. Mismatched schemas are a common source of silent failures.
